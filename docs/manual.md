# 搭建手册（正文）

> **怎么用这份文档**：把整份丢给一个会写代码的 AI（Claude / GPT / DeepSeek 都行），
> 告诉它"照着这份手册帮我搭"，它会按阶段推进并逐项验收。
>
> 本文所有路径、坐标、参数都是实测值；**坑位说明是这份文档最值钱的部分**，
> 跳过它们你会在同样的地方各花几小时——我花了六天。

---

## 一、它是什么（以及不是什么）

**是什么**：一台虚拟机里跑着 Linux 版微信（小号），一个脚本不停截图 →
OCR 认字 → 交给大模型 → 把回复打进输入框发出去。单聊、群聊（@ 才回）、
图片、表情、动图、语音都能处理。掉线能自己恢复。

**不是什么**：

- ❌ 不是微信官方接口。没有 API，全靠"看屏幕 + 模拟输入"。
- ❌ 不能群发、不能加好友、不能刷。
- ❌ 不认识的内容就是不认识（艺术字、低对比度、严重口音的语音）。
- ⚠️ 微信的界面随时可能变，**坐标和 OCR 阈值都要能重新标定**。

**适合谁**：想给自己的微信小号接一个 AI 助手，愿意花半天搭建、偶尔维护的人。

## 二、已实现特性清单

> 面向两种读者：**搭的人**知道要覆盖哪些功能（照着实现即可），
> **用的人**知道能指望什么、不能指望什么。
>
> 每一项都标注了「边界」——那是实测撞过的墙，不是理论上的顾虑。

### 2.1 读：从屏幕上认出消息

| 特性 | 实现要点 | 边界 |
|---|---|---|
| 截图取词 | `import -window root`，对话区竖切 **420px 条带 / 重叠 40px** 再 OCR | 整屏一次 OCR 会漏掉最下面那条 |
| 左右区分 | 按气泡**颜色**判：绿(≈157,242,159)=我，白=对方 | 用 x 坐标会把长消息判错 |
| 多行合并 | 同一气泡内行距小（≤26px），跨过就断 | 引用块行距 ~35px，会被误切（见下） |
| 群昵称识别 | 气泡上方灰字：短(≤12字)、最暗像素>95、紧贴、左对齐 → 记为 `sender` | 单字母昵称（`B`）OCR 读不出 |
| 引用块合并 | 形如 `昵称：内容`、紧跟上一跳、左对齐 → 并入上一条并标 `[引用：…]` | 引用的是图片时只能看到占位符 |
| 时间戳过滤 | `14:29` / `昨天 18:20` / `Yesterday23:49` / 中间带空格 | 只认这几种格式 |
| 系统消息过滤 | 撤回、入群邀请、`Convert to text` 等关键词 | 关键词表要按需扩充 |
| 头像列排除 | 丢弃 x < 80 的 OCR 行 | 头像里的字母会被读成消息（实测出现过 "W"） |
| 噪声过滤 | ≤2 字符且不含中文 → 只记日志不回复 | `ok`/`hi` 也会被跳过 |
| 媒体定位 | **墨迹密度**（文字行稀疏、图片整块密）+ 排除绿色气泡/头像列 | 黑白线稿表情没有彩色像素，不能按颜色找 |
| 只处理最新 | 媒体只取"对话最下面"的那块 | 用内容哈希去重会吞掉用户重发的同一张图 |
| 动图 | 连拍 3 帧（间隔 260ms），有变化就横拼成一张并注明"这是动图" | 只能看采样帧，不是完整动画 |
| 语音定位 | 几何 + 墨迹稀疏 + 中间大片空白；OCR 到时长算铁证 | 群聊里认不出是谁说的 |
| 语音转写 | 点气泡 → `pactl` 确认有播放流 → 录音 → **RMS 裁首尾静音** → base64 上传 | 口音重会散架；只能靠误听对照表纠名字 |

### 2.2 断：决定要不要回

| 特性 | 实现要点 | 边界 |
|---|---|---|
| 触发规则 | **只看对话最后一条是不是对方发的** | 用坐标/内容哈希当"新消息"判据都会出 bug |
| 判定即已读 | 判过的消息立刻标记，同一批不重复判 | 否则每 10 秒重判一次，烧钱又刷屏 |
| 群聊 @ 门 | **别名列表** + 归一化（去空格、全角＠转半角、小写） | 全名精确匹配会因 OCR 错字永不触发 |
| 时段规则 | 工作日 9–12、14–18 为高峰：**只回 @**；其余含周末/节假日为**空闲** | 官方峰谷规则，2026-08 起 |
| 主动插话 | 空闲时段 + 有新消息 → 带 20 条上下文判定：说一句 或 `SKIP` | 提示词里必须**鼓励 SKIP**，否则每轮硬找话说 |
| 插话护栏 | 冷却 8 分钟、每日 8 次、"最后一条必须是对方的" | 只设冷却不设上限，实测一分钟插三次 |
| 限流 | 每分钟 6 条 / 每日 60 条；**限流时保持未读** | 标记已读=永久丢消息 |
| 失败重试 | sidecar 不通时强制重扫，最多 5 次，间隔 8 秒 | 否则一条消息会因为服务未就绪被永久丢掉 |
| 上下文注入 | 群里被 @ 时带最近 6 条；上下文含自己说过的话 | 太长会被模型当成指令块 |
| 人设卡 | 每个会话一段固定背景，**改文件即生效** | 群聊和"主动插话"要分开两张卡 |

### 2.3 发：把回复送到位

| 特性 | 实现要点 | 边界 |
|---|---|---|
| 切换会话 | 列表 OCR 找会话名 → 点击 → **核对标题** → 不匹配就重试 | 列表预览行含对方名字，只匹配会话名 |
| 标题读不出 | 连试 3 次仍读不出 → **放行**并记 `title_unknown` | 死等会把会话卡死几分钟 |
| 窗口尺寸 | 每 10 轮检查宽度，不是 1920 就拉满 | 登录后窗口回到 916×666，坐标全错 |
| 粘贴 | `xclip` **后台**启动 + `ctrl+v` | 同步等 xclip 会和 ctrl+v 互锁 |
| 发送 | **点 Send 按钮** + 校验输入框清空 | `xdotool key Return` 在微信 4.x 不回显 |
| 清空校验 | 深色像素占比判断，采样避开底部工具栏 | 用"粘贴前后像素差"会误判 |
| 多会话 | 每个会话连续处理 `dwell` 轮再切 | 每轮都切会一直在等窗口重绘 |

### 2.4 活：运维可靠性

| 特性 | 实现要点 |
|---|---|
| 开机自启 | 三个 systemd 服务：Xvfb+openbox / 桥 / 看门狗 |
| 卡死自愈 | 每轮写心跳文件；看门狗发现 > 300 秒就 `pkill`，systemd 拉起 |
| 服务自愈 | 看门狗检查 `is-active`，不在就 `systemctl start`（sudoers 免密） |
| 微信自愈 | 按窗口宽度/进程判断，崩了就重启 |
| 掉线恢复 | 自动点「Log In」→ **手机分身点一下确认**（不用扫码） |
| 告警 | 掉线、服务停、桥卡死 → 邮件（30 分钟冷却） |
| 日志 | 事件化 JSONL：`incoming` / `replied` / `voice_stt` / `proactive_said` / `wrong_chat`… |
| 配置热更 | 人设卡、固定前缀 → 改完下一条消息生效 |
| 会话持久 | `chat key → sessionId` 存 JSON，重启后保持上下文 |
| 成本可见 | 日志里有每条的字节数、转写字数、模型耗时 |


## 三、架构

```
┌──────────────────── Windows 宿主机 ────────────────────┐
│  你的 AI 客户端（可选，比如 DSH / 自建 web）            │
│                                                        │
│  sidecar  ← 一个 HTTP 服务，127.0.0.1:3081             │
│    │  · 收 /inbound（文字或图片 base64）                │
│    │  · 收 /proactive（群聊自动插话判定）               │
│    │  · 收 /stt（语音转写）                             │
│    │  · 内部 spawn 一个 CLI 大模型进程（无头模式）       │
│    ▼                                                    │
└────────────────────────────────────────────────────────┘
        ▲ HTTP（10.0.2.2 是 VirtualBox NAT 里宿主的地址）
        │
┌───────┴──────── VirtualBox: Ubuntu ────────────────────┐
│  Xvfb :1 (1920x1080) + openbox                          │
│  WeChat Linux 4.x                                       │
│  bridge.py  ← 每 2.5 秒一轮：                           │
│    截图 → OCR → 解析消息 → 判断该不该回 → 打字发送       │
│  watchdog   ← 每 60 秒：微信在不在？服务活不活？        │
└────────────────────────────────────────────────────────┘
```

**为什么非要用虚拟机**：Windows 版微信是自绘界面，窗口控件拿不到；
Linux 版能在无头 X 里跑，截图和模拟点击都稳定得多。

## 四、前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| Windows | 10/11 | 装 VirtualBox 7.x |
| 虚拟机 | 4 vCPU / 4 GB / 60 GB | Ubuntu 24.04（桌面版或最小版+手动装 X） |
| 微信 | Linux 版 4.x（官方 .deb） | 只支持 x86_64 |
| 手机 | 安卓，**支持应用分身** | 关键：主微信登大号、分身登小号，两边同时在线 |
| 大模型 | 任意能命令行调用的 | 本文以 DeepSeek 为例；也可换成别的网关 |
| 语音（可选） | 阿里云百炼 ASR key | qwen-audio-asr 支持方言 |

### 手机应用分身是这套方案的"锚点"

如果没有第二台设备，小号就只能靠"断网切号"制造一个**幽灵会话**——
一切换就掉，且掉线后**必须**在电脑前扫码才能恢复。

开了应用分身之后：小号在手机上真正在线，VM 掉线后只需要**手机上点一下「确认登录」**，
不用扫码、不用在电脑前。这是整套方案能不能"无人值守"的分水岭。

## 五、分阶段搭建（每阶段都有验收）

### 阶段 1：虚拟机 + 无头显示

```bash
sudo apt update && sudo apt install -y xvfb openbox xdotool wmctrl imagemagick \
    xclip fonts-noto-cjk python3-pip
```

启动脚本（`/opt/wx-display.sh`）：

```bash
#!/usr/bin/env bash
export DISPLAY=:1
Xvfb :1 -screen 0 1920x1080x24 -nolisten tcp > "$HOME/.wx-bridge/xvfb.log" 2>&1 &
sleep 1
exec openbox > "$HOME/.wx-bridge/openbox.log" 2>&1
```

⚠️ **日志别写 `/var/log`**：服务以普通用户跑，写不进去会导致整个服务起不来，
而 systemd 的报错在别处，你会查很久。

**验收**：`DISPLAY=:1 xdpyinfo | head` 能输出 1920x1080；`DISPLAY=:1 wmctrl -l` 不报错。

---

### 阶段 2：装微信 + 首次登录

下载官方 Linux 版 `.deb`，`sudo apt install ./xxx.deb`。

启动命令：

```bash
/opt/wechat/wechat --no-sandbox --disable-audio-output
```

⚠️ **`--disable-audio-output` 不是可选项**：没有音频设备时微信会因为 PulseAudio
空指针**秒崩**（exit 139）。等以后要接语音再按第八节把音频环境配好、去掉这个参数。

**登录**：手机分身里的小号扫屏幕上的二维码（微信只认摄像头，相册里的图扫不了）。

**验收**：窗口出现且宽度 > 1000px（登录页只有 291px 宽，可以靠宽度判断是不是掉线了）。

---

### 阶段 3：标定坐标（**不能抄，必须自己量**）

最大化窗口后，用截图确认这五个数：

| 参数 | 含义 | 怎么量 |
|---|---|---|
| `region` | 对话区 (x0,y0,x1,y1) | 左侧列表右边到窗口右边，标题栏下面到输入框上面 |
| `title_region` | 顶部会话标题 | 用于确认没切到别的会话 |
| `list_region` | 左侧会话列表 | 用于点回目标会话 |
| `input_click` | 输入框里的一个点 | 点它之后能打字 |
| `send_click` | 发送按钮中心 | 见阶段 6 |

⚠️ **窗口在登录后可能回到 916×666**（不是最大化），所有坐标会全错。
所以桥必须**每 10 轮检查一次窗口宽度，不是 1920 就拉满**。

---

### 阶段 4：截图 + OCR

```bash
sudo apt install -y imagemagick
import -window root /tmp/shot.png     # 截图
```

OCR 用 RapidOCR（`pip install rapidocr-onnxruntime`）。

⚠️ **整屏 OCR 会漏掉最下面的消息**。必须把对话区**竖切成 420px 高的条带，
相邻条带重叠 40px**，逐块识别再把结果拼回去。

**验收**：截一张有 5 条消息的图，OCR 能读出全部 5 条，包括最下面那条。

---

### 阶段 5：消息解析（左右 + 分组）

一条消息在界面上可能是多行。规则：

1. **行间距 > 26px 就断开**（同一气泡内行距更小）
2. **自己发的判定用气泡颜色**：绿色（RGB≈157,242,159）是"我"，白色是"对方"

⚠️ **绝对不要用 x 坐标判断左右**：长消息气泡可以延伸到屏幕左侧，
按坐标判会把对方的消息当成自己发的。

⚠️ **采样窗口要窄**：只在气泡内取 y±3 的横带，否则会采到相邻气泡的背景色。

**群聊额外两件事**：

- **昵称行**：气泡上方有一行灰色小字（字号小、无近黑像素）。判据：
  短（≤12 字）、最暗像素亮度 > 95、紧贴下一条、左边对齐。
- **引用块**：回复别人时气泡里会多一块灰底小字（形如 `昵称：内容`），
  它和正文的行间距比正常行大（约 35px），会被误切成独立消息。
  判据：匹配 `^昵称：`、紧跟在上一条后面、左边对齐 → 归到上一条并标 `[引用：…]`。

---

### 阶段 6：发送消息

```
点输入框 → xclip 写入剪贴板（后台进程）→ ctrl+v → 点 Send 按钮
→ 截图校验输入框是否清空 → 没清空就补一次回车
```

⚠️ **`xdotool key Return` 在微信 4.x 里不生效**。文字会留在输入框里，
而脚本以为发出去了——表现为"它明明回了，我这边收不到"。
一定要**点 Send 按钮**，并把"输入框清空"作为发送成功的判据。

⚠️ **xclip 必须以后台进程启动**：它会一直等你粘贴完才退出，
同步等待会和后面的 ctrl+v **互相等死**（实测卡满 30 秒超时）。

⚠️ **输入框清空的判据别用"粘贴前后像素差"**：粘贴前框里可能还有残留文字，
发完变空反而被判成"没清空"。用**深色像素占比**判断框里还有没有字，
采样区域要避开底部那排表情/文件图标（它们也是深色的）。

---

### 阶段 7：sidecar（宿主侧的 HTTP 网关）

最小实现（Node.js，单文件）：

| 接口 | 作用 |
|---|---|
| `POST /inbound` | 文字/图片 → 调大模型 → 返回回复 |
| `POST /proactive` | 群聊上下文 → 让它决定"说一句"还是 `SKIP` |
| `POST /stt` | 语音 base64 → 转文字 |
| `GET /health` | 存活检查 |

要点：

- **令牌鉴权**：桥在虚拟机里，只有带 `x-bridge-token` 的请求才处理
- **会话映射**：`chat key → session id` 存 JSON，保证同一会话有上下文
- **调大模型走 stdin**：Windows 下走 argv 会被代码页吃掉，中文变 `????`

> **不一定要用某个特定客户端**：sidecar 里"spawn 一个 CLI"和"直接 POST 一个
> chat/completions 接口"是等价的——只要能带 system prompt + 对话历史、拿回一条文本就行。
> 用 CLI 的好处是它能自己读写文件、跑命令（能力更全）；直接用 API 更简单但只有对话能力。

⚠️ **请求体必须 `Buffer.concat(chunks).toString('utf8')`**。
用 `body += chunk` 逐片转字符串，一个汉字被切在两片之间就变乱码——
短消息没事，长消息（语音转写、长提示词）必踩。

**大模型进程的工作目录要和会话绑定**：换目录会让已保存的 sessionId 全部失效。
启动器里显式 `cd /d <固定目录>`。

---

### 阶段 8：自启与自愈

| 组件 | 机制 |
|---|---|
| Xvfb / 桥 / 看门狗 | systemd 服务，`WantedBy=multi-user.target` |
| 桥卡死 | 每轮写心跳文件；看门狗发现心跳 > 300 秒就 `pkill`，由 systemd 拉起 |
| 服务被停 | 看门狗检查 `systemctl is-active`，不在就 `systemctl start`（配 sudoers 免密） |
| 微信崩了 | 看门狗按窗口宽度判断，宽度 < 300px 或进程不在就重启微信 |
| 掉线 | 看门狗自动点「Log In」，手机分身弹确认 |
| 通知 | 以上异常发邮件（SMTP），30 分钟冷却 |

⚠️ **systemd 依赖环**：如果 `wx-xvfb.service` 里写了 `After=multi-user.target`，
而桥又 `After=wx-xvfb`，会形成环 → systemd **直接丢掉桥的启动任务**，
表现为"重启后桥根本不启动"，日志里只有一行 `Found ordering cycle`。

## 六、六个关键设计决定（照抄能省很多时间）

| # | 决定 | 为什么 |
|---|---|---|
| 1 | "新消息"只看**顺序**：最后一条是不是对方发的 | 用坐标当指纹会因滚动失效；用内容哈希会"同一句话永不再回" |
| 2 | 群聊只回 **@**，@ 用**别名列表** + 归一化（去空格、全角＠转半角） | 全名精确匹配会因 OCR 错字而永远不触发 |
| 3 | 媒体用**墨迹密度**找，不用颜色 | 黑白线稿表情没有彩色像素；文字行墨迹稀疏 |
| 4 | 只处理**最下面那块**媒体，不按内容去重 | 用户重发同一张图是正常操作，按内容去重会吞掉它 |
| 5 | 判定过的消息**立即记为已读** | 否则同一批消息每 10 秒重判一次，烧钱又刷屏 |
| 6 | 主动插话只在**空闲时段** | 谷时价格是高峰一半；晚上群里才有人 |

## 七、十五个坑（按踩到的顺序）

| # | 症状 | 原因 | 做法 |
|---|---|---|---|
| 1 | 微信一启动就崩（exit 139） | 没有音频设备，PulseAudio 空指针 | 加 `--disable-audio-output` |
| 2 | OCR 读不到最下面的消息 | 整屏识别丢底部 | 竖切 420px 条带，重叠 40px |
| 3 | 机器人回自己的话 | 用 x 坐标分左右 | 改用绿色气泡颜色 |
| 4 | 长消息被当成别人的 | 采样窗口太高，采到相邻气泡 | 只取 y±3 横带 |
| 5 | 它说回复了但对方收不到 | `xdotool key Return` 在微信 4.x 无效 | 点 Send 按钮 + 校验输入框清空 |
| 6 | 发送流程卡 30 秒 | xclip 同步等待，和 ctrl+v 互锁 | xclip 后台启动 |
| 7 | 每次重启后所有会话失效 | 工作目录变了，sessionId 全部判废 | 启动器里 `cd` 到固定目录 |
| 8 | 中文变 `????` | CLI 走 argv，Windows 代码页 | 任务正文走 stdin |
| 9 | 标题读失败时反复重点会话 | OCR 偶发返回 `?`，被判成"切错了" | 读不出标题时**不判定为切错** |
| 10 | 找单聊却点开了群 | 列表预览行里含对方名字 | 只匹配会话名（带冒号的行是预览） |
| 11 | 突然回一句 "又一个 W" | 头像里的字母被 OCR 读成消息 | 丢弃 x < 80 的 OCR 行 + 噪声过滤 |
| 12 | 同一张图连回五遍 | 检测框抖动导致哈希变化 | 按位置关系判"是否最新"，不用哈希 |
| 13 | 同一句话回一次后永远沉默 | 文本哈希去重 | 用顺序判定，去掉内容去重 |
| 14 | 连发三条只回两条 | 限流时把消息标记成已读 | 限流时**保持未读**，等配额窗口过去再回 |
| 15 | 重启后发消息没反应 | 重启时把屏幕上的消息全标成已读 | 重启后补一次判定，或让用户重发一条 |

### 语音专章（如果要做）

语音是这套里最容易踩坑的部分，四个连环坑：

| 症状 | 原因 | 做法 |
|---|---|---|
| 有语音却不处理 | 气泡右侧的 `Convert to text` 被 OCR 读成消息，且比气泡更靠下 | 落在语音块纵向范围内的文本一律丢弃 |
| 只发语音时永远没反应 | `if not incoming: continue` 排在基线逻辑之前，语音被剔除后 incoming 恒空 | 语音段必须放在该判断**之前** |
| 语音处理了但文字不回 | 语音分支的 `continue` 写在了"冷却已过"那一层，只要有语音块就每轮跳过文字 | `continue` 只放在"真的点开语音了"里面 |
| 录到的时长是实际的 1.7 倍 | 微信播完后音频流还会挂几秒，"流结束"不等于"语音结束" | 录完按 RMS 裁掉首尾静音 |

音频环境（Ubuntu）：

```bash
sudo apt install -y pulseaudio pulseaudio-utils alsa-utils
sudo usermod -aG audio $USER
sudo modprobe snd-aloop
export XDG_RUNTIME_DIR=/tmp/xdg
pulseaudio --start --exit-idle-time=-1
# sink 选 alsa_output.platform-snd_aloop.0.analog-stereo
# 录音用 parecord --device=<sink>.monitor
```

## 十、已知限制

| 限制 | 说明 |
|---|---|
| 群里语音认不出是谁说的 | 语音没文字，只能知道"有人说了这句" |
| 文件/视频消息 | 只能看到"这是个文件" |
| 艺术字、低对比度文字 | OCR 读不出来 |
| 严重口音的语音 | 会散架（把"吃火锅"听成"吃果"这种），可在配置里写误听对照表 |
| 微信升级 | 界面变了就要重新标定坐标 |
| 成本 | 每条消息一次模型调用；OCR 约占 9% 单核 |

## 十一、成本量级（参考）

虚拟机常驻：4 vCPU / 4 GB，OCR 约 9% 单核。

模型调用：一条消息一次，纯文字约几百 token；
带图/带语音约几千 token。**按空闲时段用，成本减半。**

主动插话是额外开销：每次判定一次调用（带 20 条上下文），
设 8 次/日上限的话，一晚上不到十次。

## 附：一句话总结

> 这套方案的本质是"**让 AI 看屏幕、替你在微信里打字**"。
> 难点从来不是调模型，而是**屏幕上的位置和顺序都不可靠**——
> 凡是拿坐标或哈希当身份判断的地方，最后都会变成 bug。
